Architecture walkthroughs

Nine security projects, from proof of concept to signed-off production.

Six years in a regulated bank across seven countries, as its estate grew from about 8,000 endpoints to about 18,000 assets. Pick a project to see how it was designed, the options we turned down, how it was built and how we proved it worked.

Written from my own experience with no employer documents. The bank is not named, and anything an attacker could use has been left out. Ports and URLs are vendor-standard values.

Led: I owned deliverySecurity ops lead: vendor or another team built itSupported: a defined part, named inside
01 · Endpoint protection

SentinelOne on-premises to cloud

LedPrimary SentinelOne administrator · first security product the bank moved to the cloud

Running our own console meant owning its upgrades, its operating system and its certificates, and an expired certificate once took a whole entity's agents offline. Moving management to the vendor's cloud removed that work, but no security product had left the data centre before, so the regulator had to approve where its data lived.

DecisionWe choseBecause
Regulator first or build firstRegulator firstApproval on data retention, metadata and deletion had to exist before any agent moved. I collected the vendor's answers and wrote the case.
Fresh policy build or replicateReplicate every policy, exclusion and blocklist entryProtection must be identical the moment a device changes console.
Cut over or keep a fallbackKeep the on-premises console liveA rollback is only real while the old service, licences and access still exist.
Every entity or regulated scopeTwo entities stayed on-premisesTheir local regulation did not allow the move.
How it was built
  • Tenant laid out as one site per entity, with groups by device type, so each country had delegated administration and inherited policy.
  • Agents talk to the tenant on TCP 443. The web proxy bypasses inspection for the vendor domain.
  • Waves: IT users, then departments, then the VDI (Virtual Desktop Infrastructure) gold image, then test servers, then production servers in planned outage windows.
  • Each agent release was tested first on laptops, VMs and cloned production servers, with threat and CPU-load tests.
  • Administrators sign in with role-based access. Reporting reads the console through a read-only API (Application Programming Interface) token.
  • Before migration: on-premises console backed up, and the cloud retention period checked against the bank's requirement, with longer-term logs kept in the SIEM.
Gates passed
  • Vendor data questionnaire
  • Risk committee
  • Central bank approval
  • CAB per wave
  • On-prem retirement record
A wave closed when every device in it was online in the cloud console on the right policy, a test detection reached the SIEM (Security Information and Event Management), and no device was left on the old console without a ticket.
In one minute

It was the bank's first security product in the cloud, so the hard part was the approval, not the technology. I gathered the vendor's answers on retention, metadata and deletion, wrote the case for the central bank and presented the benefits against the risks to CAB and the risk committee. Technically, we replicated every policy before moving a single agent, moved in waves with servers only in outage windows, and kept the old console alive as rollback until the last wave closed.

02 · Web and egress

Blue Coat proxy to Zscaler ZIA

Security ops leadThen ZIA policy, SSL inspection and blocklist administrator

The on-premises Blue Coat proxy only protected people sitting on the bank network, and it was being withdrawn, so the deadline was fixed. Losing web filtering in a bank was not an option. Internet access moved to Zscaler Internet Access, a cloud proxy reached through an agent on each device.

DecisionWe choseBecause
Big bang or staged under a deadlineStaged: a 50-device control group, then about 800 hand-picked users across every entity, then the restThe 800 covered every country, department and application mix, so the working model was proven everywhere before the bulk moved. Blue Coat stayed in place for anyone not yet moved.
Inspect everything or bypass broadlyInspect by default, with an approved bypass listEach bypass needed a business owner and a reason, so the list could not quietly become a hole.
Roll a user back or relax one ruleRelax one rule for one group, fix, then restoreThe business kept working and no exception became permanent.
New joiners on old or new proxyStraight to ZscalerA new-hire access group stopped the old proxy's population growing.
How it was built
  • Bank root certificate and the Client Connector pushed to devices before any traffic moved.
  • Client tunnels to the nearest Zscaler service edge on 443. Users sign in once through the identity provider (SAML, Security Assertion Markup Language), and group membership drives policy.
  • Policy order: direct bypass, do-not-inspect list, URL categories, cloud app control, DLP (Data Loss Prevention) on uploads, file-type rules, threat blocklists.
  • Market data feeds, log transfers and in-house applications that broke under inspection were each fixed with a tested, owned bypass.
  • Web logs streamed to the SIEM for investigations and audit evidence.
Gates passed
  • 50-device control group in Bahrain
  • 800 users across all entities
  • Application test per department
  • CAB per user group
  • Bypass approvals by owner
  • Blue Coat decommission record
Blue Coat was switched off when no user traffic had reached it for an agreed period, no critical tickets were open, and block pages, DLP tests and SIEM log search all worked from Zscaler.
In one minute

Blue Coat was being withdrawn, so we had a fixed deadline and couldn't leave the bank without web filtering. We started with a 50-device control group in Bahrain, then about 800 hand-picked users across every entity, from Bahrain to the UK, so every country and application mix was tested before the bulk moved. The real work was the breakages: data feeds, log transfers and in-house apps that failed under SSL inspection. Each got an owned, approved bypass instead of a blanket exception. When the 800 raised critical tickets, I relaxed one rule for one group, fixed it and put it back, so the business never stopped and no hole stayed open.

03 · Endpoint protection and identity

SentinelOne to Microsoft Defender, Intune and Entra ID

LedRan the PoC, then the bank's technical lead with the vendor across six countries

The bank consolidated on its Microsoft 365 E5 licence: Defender for Endpoint for protection, Intune for device policy and Entra ID for identity, replacing SentinelOne and Trend Micro. The one design rule was that no device could be unprotected at any point in the change.

DecisionWe choseBecause
Rip and replace or overlapShort overlap on each device, Defender running passiveThe old agent stays until the new one is proven, so the device is never bare.
Wave orderHeadquarters first: IT users, departments, test, database, then production servers; other entities afterProblems surface where support is closest, and the riskiest servers go last.
What closes a waveEvery agent online and its alerts reaching the SIEMAn agent count proves installation, not protection.
One onboarding method or severalIntune for managed workstations, scripts and group policy for serversServers and unmanaged devices could not wait for Intune enrolment.
How it was built
  • Defender sensor talks to Microsoft on 443. Zscaler bypasses inspection for Microsoft security endpoints, a policy I built when connectivity blocked onboarding.
  • During the overlap Defender antivirus ran passive with the EDR (Endpoint Detection and Response) sensor still recording. On Windows Server, passive mode is set before onboarding.
  • Per-device check, scripted: sensor registered and healthy, old agents removed, reboot, antivirus mode Normal, test alert raised and received.
  • Intune applied antivirus, attack surface reduction and baseline profiles. Exceptions followed the same ticket, approval and expiry rule as before.
  • A device that failed after removal was isolated from the network, reinstalled and retested.
Gates passed
  • PoC against the incumbent
  • Risk and data location review
  • CAB per wave and entity
  • SOC acceptance
  • SentinelOne and Trend Micro decommission
When onboarding fell behind plan, I broke the gap down by cause: network connectivity, agent conflicts and offline devices. I fixed the connectivity cases myself, gave infrastructure a named list for the rest, and reported wave by wave so the numbers could be explained, not just increased.
In one minute

I led the Defender PoC against our incumbent, then the rollout across six countries. The rule was that no device is ever unprotected. Defender went on first in passive mode. We proved it was registered and healthy, removed SentinelOne and Trend Micro, rebooted, and proved Defender was active and its alerts reached the SIEM. A wave didn't close on agent counts. It closed when every device was proven.

04 · Data discovery

BigID data discovery, PoC to production

Security ops leadThe privacy team owned classification. I made it safe to scan.

The bank needed to know where personal and sensitive data lived before it could label, protect or retain it, and to support privacy work such as records of processing and data subject requests. BigID scans data stores and reports what it finds.

DecisionWe choseBecause
Where scanning runsScanners inside the bank, next to the sourcesRaw data never crosses the network boundary.
Access to each sourceOne read-only service account per source, approved by its ownerNo shared, high-privilege account that opens every system.
How wide the PoC wentAbout five sources, one per technologyProves connectivity, accuracy and load before scaling.
Vendor accessNamed, time-boxed and monitoredVendor activity checked against approved scope.
How it was built
  • Standard connector paths: file shares over SMB (Server Message Block) 445, databases on their listener ports, Microsoft 365 through Graph on 443.
  • Each source onboarded through its own network rule, owner approval and service account.
  • Database scans scheduled off-hours so production was not slowed.
  • Access split by role: privacy administration, security audit, and data owners seeing only their own sources.
Gates passed
  • PoC success criteria
  • Data owner approval per source
  • Network change per source
  • Vendor access approval
  • Handover to privacy team
My part: progress reporting to management, unblocking access with application owners and the network team, and monitoring vendor activity in bank environments.
In one minute

On BigID I led for security operations; data classification belonged to our privacy colleague. My job was making scanning safe: scanners inside the bank so data never left, read-only accounts approved by each owner, network rules per source, and watching the vendor's activity against the approved scope. We proved it on about five sources before scaling.

05 · Network detection

Darktrace network detection, PoC to production

Security ops leadThe network team deployed sensors. I ran the security side and tuning.

Endpoint agents only see devices that have agents. Darktrace watches copies of internal traffic and learns normal behaviour, so it can flag lateral movement, unusual data transfers and unmanaged devices that the EDR cannot see.

DecisionWe choseBecause
Inline or mirrored trafficMirrored (SPAN, Switched Port Analyzer) feedsNo risk to production traffic.
Alert on day one or learn firstLearning period, then tuning with the SOCBehavioural models need a baseline before alerts mean anything.
Silence noisy models or tag devicesTag known tools such as vulnerability scannersThe model still catches an attacker doing what the scanner does.
Separate console or one queueAlerts into the SIEMAnalysts work one queue.
How it was built
  • Core and data-centre switches mirror traffic to sensor capture ports, so east-west traffic between servers is visible.
  • Sensors send metadata to the master on 443. The master forwards alerts to the SIEM by syslog.
  • Enrichment from directory and DNS (Domain Name System) data maps addresses to devices and users.
  • Early noise fixed by tagging: our own Qualys scans looked like lateral movement until the scanners were labelled.
Gates passed
  • PoC on selected segments
  • Network change for mirror sessions
  • Tuning sign-off with SOC
  • SOC runbooks and handover
Ready for the SOC when sensors showed traffic from every planned segment, the noisiest models had been reviewed, and each alert type had a triage runbook and escalation path.
In one minute

Darktrace gave us east-west visibility that endpoint agents couldn't. It's passive: mirror ports feed the sensors, so if a sensor fails, production doesn't notice. The network team placed the sensors and I ran the security side. In the first weeks our own Qualys scans looked like lateral movement. Instead of muting the model, I tagged the scanners, so a real attacker doing the same thing would still be caught.

06 · Asset visibility

Lansweeper scanning to agent and cloud

SupportedLansweeper was one of the ten sources in my control-coverage reconciliation

Network scanning only finds devices that are connected when the scan runs, so remote laptops went stale. It also needs an account with admin rights on every machine. Moving to the Lansweeper agent fixed both problems, and the cloud link gave one view across entities.

DecisionWe choseBecause
Agentless, agent or bothAgent on endpoints and servers, read-only SNMP for network devicesEach device type gets the method it supports.
Domain-wide scanning accountRetired once agent coverage was confirmedRemoves a high-value credential from the estate.
Off-network laptopsReport through the cloud relay on 443No dependence on VPN connection.
How it was built
  • LsAgent reports to the scanning server on the network, or through the Lansweeper cloud relay on 443 when off-network.
  • The on-premises installation links to a Lansweeper cloud site for a multi-entity view.
  • Agent added to gold images so new builds report from day one.
Why it mattered
Inventory is the denominator. Every coverage figure in the CISO report divided by it. A stale inventory makes every protection percentage wrong, so new records were reconciled against the directory, Defender and ManageEngine.
07 · Hardening

Minimum security baseline

SupportedI tested controls and cleared false positives

Devices built at different times had different settings, and nobody could prove the estate met one standard. The baseline set one hardening standard per platform, built from CIS (Center for Internet Security) Benchmarks, then enforced and measured it.

DecisionWe choseBecause
Write from scratch or adoptAdopt CIS and tailorDefensible to auditors and faster to agree.
Enforce or measure firstMeasure in audit mode, fix, then enforce by waveApplication breakages surface before they hit users.
Trust the scanner or verifyVerify each failed check on a test machineA report full of false failures gets ignored.
Typical settings in scope
  • SMBv1 and LLMNR (Link-Local Multicast Name Resolution) disabled; NTLMv2 only.
  • Unique local administrator passwords (LAPS, Local Administrator Password Solution).
  • BitLocker on laptops, screen lock on idle, host firewall on all profiles.
  • Audit policy and PowerShell logging on.
My part
When the scanner said a control failed, I proved on a test machine whether it really failed, the check was wrong, or a compensating control existed, before anything was raised to an owner.
08 · Resilience

Disaster recovery exercises for security platforms

SupportedAnnual drills and semi-annual rehearsals; four crisis war rooms

Applications come up at the recovery site, but the agents, proxy path, certificates and log forwarding often were never tested there. My part of each drill was proving that security controls followed the workload.

CheckBefore failoverAfter failover
Endpoint agentsRecovery servers listed, online, on the right policyOnline from the recovery network; test alert raised
Internet pathEgress rules and bypasses exist at the recovery siteBrowsing filtered; critical feeds still work
LoggingCollectors configured at the recovery siteEvents from recovery hosts reach the SIEM
CertificatesConsole and inspection certificates checked for expiryNo certificate errors on agents or browsers
Lesson carried into every drill: one forgotten dependency, an expired console certificate, once took several hundred agents offline in one entity. Certificate expiry checks went into the drill checklist, and expiry reminders went to a team mailbox with the impact spelled out.
09 · Assurance and reporting

Control status reporting to the CISO

LedBuilt the workbook, wrote the biweekly pack, then presented it

Each security tool reported its own coverage, and each one looked good on its own. Joined together against the asset inventory, they told a different story. This was not a CAB change. It was a reporting line straight to the CISO and senior management, and it is how the 478 devices that looked protected but were not came to light.

How it was built
  • Exports from ten tools, including the EDR consoles, Qualys, ManageEngine, Lansweeper, Intune and the directory, matched per device against the inventory.
  • SentinelOne data pulled straight into Excel through its API with Power Query, so the figures were not retyped.
  • Each device rated on whether its controls were present and actually working, not just installed.
  • Agile in practice: the pack changed every cycle as leadership asked new questions.
Governance
  • No CAB: reporting only
  • Biweekly to CISO
  • Senior management review
  • Figures reconciled wave by wave
Why it mattered: a console counted those 478 devices as covered. The joined view showed they were not. 180 active user machines were reinstalled and the rest were triaged.
In one minute

Every tool said coverage was fine, so I joined ten of them against the asset inventory, device by device. That showed 478 devices the console counted as protected that weren't. I wrote the biweekly control pack for the CISO and later presented it myself, which meant defending every figure. That's why I reconciled wave by wave instead of quoting totals.

How a change got from idea to production

None of these platforms went live because the technology worked. Each moved through the same eight stages, and each stage left a record that an auditor, the CISO (Chief Information Security Officer) or CAB (Change Advisory Board) could ask for. Click a stage.

Stage 1

Proof of concept

Record produced:

Every platform here went in by phased waves or a parallel run, never big bang. A security agent touches every device, so a bad setting in a big bang breaks the whole estate at once and leaves no healthy group to compare against. Agile suited the reporting work, which improved in short cycles, but not production rollouts, which need fixed CAB windows.

  • Functional: policy applied, device visible, response actions such as isolation work.
  • Load: CPU and memory measured on laptops, VMs and cloned production servers under normal and heavy work.
  • Security: safe test files and simulated attacker behaviour, with the SOC (Security Operations Centre) told in advance so alerts could be matched to the test.
  • Tamper: try to stop or uninstall the agent as a local user. It must refuse.
  • Availability: after go-live, daily checks for offline or unhealthy agents, using the offline-agent runbook before escalating to the vendor.
  • On-premises servers: staged on a hardened build, vulnerability-scanned clean, admin accounts in the privileged access vault with password rotation, backups taken and a restore tested.
  • Cloud services: outbound path on 443 through firewall and proxy, inspection bypass where needed, tenant data location confirmed.
  • Log retention: how long the platform keeps events, checked against the bank's requirement. Where it kept less, logs went to the SIEM (Security Information and Event Management), which holds them longer.
  • Certificates: expiry dates recorded, with reminders to a team mailbox.
